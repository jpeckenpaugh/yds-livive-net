## 2. The four files

Approved exactly as laid out in PM ruling Q4, with one addition for M1. Paths are normative.

**The convention is `src/data/conversations/<id>.{source.json,json,glossary.json}` and `src/data/glossary.es.json`, where `<id>` is the conversation's id.** In M1 `<id>` is **`m1-fixture`**; at M2 the shipping conversation takes its own id and the fixture is deleted (amendment F1). The fixture is *not* at the shipping conversation's path, which is what D1 §4 requires — it is a distinct conversation that happens to be the only one M1 has.

| File | Authored by | Machine-written | In git | M1 path | Contents |
|---|---|---|---|---|---|
| authored source | **human** | never | yes | `src/data/conversations/m1-fixture.source.json` | `ConversationSource` — English only, templates allowed |
| authored gloss overrides | **human** | never | yes | `src/data/glossary.es.json` | keyed by `normalizeSpan(text)` |
| generated artifact | machine, then possibly human | yes | yes | `src/data/conversations/m1-fixture.json` | `Conversation` — slot-free runtime artifact |
| generated glossary | machine | yes | yes | `src/data/conversations/m1-fixture.glossary.json` | `GlossIndex` |
| conversation entry module | **human** | never | yes | `src/data/conversation.ts` | **the sole importer of `conversations/*.json` in `src/**`**; exports `CONVERSATIONS: Conversation[]` (amendments F1, Y2) |
| flag list | review agent, then adjudicated by the owner | — | yes | `review/flags.m1-fixture.json` | §8 |
| coverage report | machine | yes | yes | `review/report.m1-fixture.md` | §9, regenerated, never hand-edited |

### 2.1 The conversation entry module (amendments F1, Y2)

```ts
// src/data/conversation.ts — the single entry point
import type { Conversation } from '../domain/types';
import fixture from './conversations/m1-fixture.json';

const artifacts: unknown[] = [
  fixture, // M1 fixture; deleted in M2
  // content conversations, generated by `npm run bake:content`
];
export const CONVERSATIONS: Conversation[] = artifacts as Conversation[];
```

**One module, one array.** `src/data/conversation.ts` is the **sole** importer of `conversations/*.json` in `src/**` (AC-CONTENT-22) and exports `CONVERSATIONS: Conversation[]`. `src/data/catalog.ts` derives its entries from that array, and `src/ui/**` reaches content only through the catalog or `conversationById`. A UI component that reaches for a conversation JSON directly breaks the swap, and review catches it because there is exactly one module to look at.

**The M2 swap is one array entry plus one deletion** (amendment Y2). The earlier claim — "one import path plus one deletion" — described a single-conversation module and is now stale. Adding the shipping artifact is one array entry (its `import` plus its line in `artifacts`); retiring the fixture is deleting its entry and its files. Nothing in `src/ui/**` changes. The entry module was deliberately made a list so the catalog (M5) could hold more than one conversation without re-plumbing the UI, and that is exactly what makes the content swap a data edit rather than a code edit.

**The fixture *is* in the M1 bundle** (PM ruling F1). D1's earlier wording — "the fixture never ships" — was wrong; the correct statement is that the fixture is never the *shipping content*. A smoke test over `dist/` needs the conversation in `dist/`, and M1 must be playable end to end, so bundling it is the point.

### 2.2 The fixture's review policy (amendment F2)

The fixture must not claim `reviewedBy: 'owner'` — that would assert a human review that never happened, and the Engineer was right to refuse. The mechanism is `ConversationMeta.reviewPolicy` (D2 §7.2), recorded **in the artifact** rather than inferred from a path, so it survives a move and shows up in a diff:

| `reviewPolicy` | `E_UNREVIEWED` | `E_EDITED_NOT_OWNER` | Extra rule |
|---|---|---|---|
| `'shipping'` | error | error | — |
| `'fixture'` (M1) | **warning** | **warning** | `reviewedBy: 'agent'` and `l2 === mt` are required; `reviewedBy: 'owner'` is an **error** |

So the fixture passes the gate with `reviewedBy: 'agent'` and `l2 === mt` — both already permitted by D2 §7.2 — while the artifact itself records that no triage agent ran. The report prints the policy on every run, and `bake:check` fails if a `'fixture'` artifact is ever referenced as shipping content at M2.

**The mechanism that sets the policy is `--review-policy <shipping|fixture>`** (amendment E1), which **defaults to `'fixture'`** — omitting it can never claim a human review, which is the property that matters. D5 §3 owns the flag.

### 2.4 How the committed fixture is produced (amendment E2)

An earlier revision of §7.2 said a fixture run with no translator writes `l2 = mt = ''` and "coverage fails loudly". That contradicted F1/F2 — which require a **complete, playable** artifact with `l2 === mt` and full gloss coverage — and it made `bake:check --author-only` unable to exit 0. Both cannot hold. The resolution, **confirmed**:

> The committed fixture is generated **once**, by `bake:fixture`, using the **fixture translator** (the deterministic fake of §4.2). `--author-only` is **never** run in write mode against the fixture. `bake:check --author-only` validates the committed artifact and exits 0.

That is coherent on every axis, and it is the only arrangement that satisfies all four constraints at once:

| Constraint | How it holds |
|---|---|
| the fixture is complete and playable (F1) | the fixture translator fills every `l2` and every gloss span |
| `l2 === mt` for every record (F2) | the fixture translator's output *is* `mt`; nothing edits it |
| `bake:check --author-only` exits 0 | it validates a committed artifact and never drafts |
| **CI never generates** (the standing rule) | the fixture is regenerated only by `bake:fixture`, on a dev machine, as an explicit act |

The fixture translator is **deterministic**, so regenerating the fixture produces a byte-identical artifact and `bake:check`'s idempotence assertion (AC-CONTENT-03) covers it. That is also why the fixture's Spanish is not real MT: real MT would make the committed artifact unreproducible offline, which would put a 214 MB model download behind every fixture regeneration and break the standing rule. `meta.reviewPolicy: 'fixture'` is what records that this text is a scaffold rather than teaching material, and the artifact is deleted at M2 (F1).

**Two concessions the fixture makes, and neither may be inherited by M2:**

1. **Glosses.** Sub-span gloss entries in the fixture are **identity mappings** — `l1 === mt === spanText`, `origin: 'mt'`, `reviewedBy: 'agent'`. Coverage is complete (`E_GLOSS_MISSING` is satisfied), but a self-gloss teaches nothing. This is acceptable only because the fixture is never taught from and is deleted at M2. The guard is mechanical: a **`'shipping'`** artifact whose gloss `l1 === mt === spanText` is an error, `GLOSS-IDENTITY` (§12). Only line-level spans carry real English in the fixture.

   **The guard inspects `origin: 'mt'` entries only** (amendment Y6). That is not a per-conversation escape hatch: the only authored-gloss route is the **global** `glossary.es.json` (D2 §3, §9.4), which is human-owned and shared across conversations, so a shipping artifact cannot mint a private identity gloss by relabelling it `origin: 'authored'`. In practice **every shipping gloss is `origin: 'mt'`** and must be genuinely non-identity; an authored override that merely restates the span is still a wart, but it is not the mechanism the fixture uses and it is not how any conversation's coverage is satisfied.
2. **Translator provenance.** `meta.translator` is the fixture identifier `fixture-1`, not a pinned SHA (D2 §7.2). A `'shipping'` artifact's revisions must be a **pinned revision id of the required kind** — a model SHA from D3 §10.2 **or** an `authored-<n>` authored-table revision (amendment Y1). An authored table is a legitimate injected translator, and its revision must be recorded honestly rather than replaced by a model SHA that never ran.

**M2's boundary, stated once so it is not rediscovered:** the shipping artifact must have a **real gloss at every level** (`line`, `sentence`, `clause`, `predicate`), no identity entries, **a real, recorded translation provenance** — a model SHA or an `authored-<n>` table revision, never a fabricated model revision (amendment Y1) — and `reviewPolicy: 'shipping'` with every record adjudicated. AC-CONTENT-25 asserts the first three against the M2 artifact and the fixture's exemption is what makes them M2 criteria rather than M1 ones.

Edit rules (D2 §3, restated as instructions because this is the doc an author reads). `<id>` is `m1-fixture` in M1:

1. **Never hand-edit `<id>.glossary.json`.** Gloss corrections go in `glossary.es.json`.
2. `<id>.json` **may** be hand-edited, but only the `l2` field of a variant record. Nothing else. A hand-edited `l2` is detected, not declared (§7.2).
3. The `.source.json` is the only place templates, hints, labels and variables live.
4. No timestamps in any generated file.
5. `review/flags.*.json` is edited only to adjudicate (§8.4).
6. **`src/data/conversation.ts` is the only module that imports a conversation artifact** (F1). Nothing under `src/ui/**` may import a `.json` conversation directly.

## 3. Two axes, and the CLI surface

The pipeline has exactly two axes, and conflating them is the main way to get confused about `--author-only`:

| Axis | Values | Meaning |
|---|---|---|
| **mode** | `write` \| `check` | `write` may modify the artifact. **`check` never writes anything** and is the only mode CI runs. |
| **translator** | provided \| **absent** (`--author-only`) | Whether machine drafting is available in this run. |

```bash
bake --conversation <path>                       # write + translator (dev machine, full drafting)
bake --check --conversation <path>               # verify only; needs no translator at all
bake --check --author-only --conversation <path> # CI default (PM ruling): verify structure, hashes,
                                                 # provenance, coverage, revisions. Zero network.
bake --author-only --conversation <path>         # write + no drafting: author by hand; MT fields stay empty
bake --prune --conversation <path>               # write: remove orphaned variant/gloss records
bake --report --conversation <path>              # write review/report.<id>.md
bake --adjudicate review/flags.<id>.json         # apply an adjudicated flag list (§8.4)
```

**`--conversation <path>` selects the authored source** (amendment E2). It is required, and it is what makes M1 and M2 differ by one argument: M1 points it at the development fixture, M2 at the shipping conversation. An earlier revision fixed the input path, which M1 does not have — the fixture is not at the shipping conversation's path (D1 §4).

M1's invocation is therefore:

```bash
bake --check --author-only --conversation src/data/conversations/m1-fixture.source.json
```

**`--check --author-only` is the CI default and the reason the pipeline is testable.** It validates a committed artifact offline, against pinned revisions recorded *in* the artifact, with no model downloads. `check` + a translator present is allowed and additionally verifies that fresh MT output still matches (it reports `E_SOURCE_STALE`/`E_TRANSLATOR_REV_STALE` rather than writing).

**`--author-only` in `write` mode is not a way to produce a shippable conversation from scratch.** It cannot fill ~200 gloss spans, so coverage will fail. Its purposes are CI verification and hand-authoring a line or two before a full bake. This is why the PM's ruling that author-only is the CI default is coherent: its job is *verification*, not generation.

**The first full bake needs an install** (amendment F3): `npm i -D @huggingface/transformers` — the runtime is a devDependency that M1 deliberately does not carry, and `tools/bake/translator.node.ts` imports it lazily inside the injected port (D3 §10.8).

## 4. Pipeline phases

Each phase is a pure function over the previous phase's output, so any phase can be tested alone. Phase 0 is the only one that needs a model.

| # | Phase | Input | Output | Fails with |
|---|---|---|---|---|
| 0 | **Model smoke test** (skipped when the translator is absent) | the `Translator` | proof that `>>es<<` is honoured (§4.1) | abort before any drafting |
| 1 | **Validate source** | `.source.json` | `Diagnostic[]` | any `E_*` error from D2 §14 |
| 2 | **Enumerate** | source | `WalkStep[]` (exhaustive, D2 §5.1) + the variant spec set | `E_NO_MATCH`, `E_AMBIGUOUS_MATCH`, `E_DEAD_ALTERNATIVE`, `E_ENUM_LIMIT_*` |
| 3 | **Render English** | variant specs | one `l1` per variant spec; `sourceHash` per `l1` | `E_VARIANT_KEY_COLLISION` (§5.3) |
| 4 | **Draft L2** | `l1` strings + `Translator` | `mt` per variant; `translationRev` | translator errors are fatal, never silently skipped |
| 5 | **Segment** | each variant's `l2` | the distinct span key set, all levels (D2 §9) | `SEGMENTATION_VERSION` mismatch |
| 6 | **Draft glosses** | span keys + `Translator` (ROMANCE-en) | `mt` per `GlossEntry` | as phase 4 |
| 7 | **Merge, stamp, assemble** | everything above + `glossary.es.json` + the flag list | `Conversation` + `GlossIndex` + edits to the flag list only if adjudicating | `E_UNREVIEWED`, `E_EDITED_NOT_OWNER`, `E_GLOSS_*`, `E_L2_RESERVED_CHAR` |
| 8 | **Report** | the assembled artifact | `review/report.<id>.md` + exit code | `E_*` from the `check` pass |

Phase ordering is load-bearing: **glosses are generated from the drafted `l2`, not from the English.** A gloss is a rendering *of a piece of the Spanish*, because that is what the learner is hovering.

### 4.1 Phase 0 — the sentinel smoke test

D3 §10.3 owns the fact; this is where it runs. `opus-mt-en-ROMANCE` selects its target with a sentence-initial `>>es<<` token. If the sentinel is ignored, the model returns Portuguese for a Spanish page and **nothing errors**. So before any drafting:

```
assert translate({ text: 'Do you want to get together tomorrow?', from: 'en', to: 'es' })
    !== translate({ text: 'Do you want to get together tomorrow?', from: 'en', to: 'pt' })
```

A failure aborts the run with `E_SENTINEL_IGNORED` (**proposed D2 registry addition**, see §12) and no artifact is touched.

### 4.2 Translator injection (R6 — the testability contract)

```ts
type BakeInput = {
  source: ConversationSource;
  prior?: Conversation;                       // the committed artifact, if any
  translator: { en2romance: Translator; romance2en: Translator } | null;
  mode: 'write' | 'check';
  prune?: boolean;
  adjudication?: AdjudicatedFlagList;
};

type BakeResult = { conversation: Conversation; gloss: GlossIndex; diagnostics: Diagnostic[] };
```

The translator is a **parameter, never a module-level import**. Tests pass a fake — a deterministic lookup table plus a recorded "mangled" output for each fixture string — and the whole pipeline runs with zero network, zero downloads and byte-stable output. This is the single most important decision for the Engineer's self-verification (PM R6), which is why it is a frozen port rather than an internal helper.

The fake must be able to produce **wrong** output on demand, so the triage path is testable: a fake whose Spanish is deliberately Portuguese for one fixture must produce a flaggable entry, not a crash.

## 5. Enumeration and emission

### 5.1 What is enumerated

For every variant spec from D2's exhaustive walk (§D2 5.1), the pipeline emits exactly one `VariantRecord`:

- one per **fixed-beat alternative** × each distinct tuple of values for that alternative's `slotNames`;
- one per **option** × each distinct tuple of values for that option's `slotNames` (which include the option's own `sets`, D2 §5.1).

Ghosts and previews need no extra records: an option's variant **is** the line used for the chosen response, the ghosted road not taken, and the preview (D2 §11.2).

### 5.2 Emission rules

| Rule | Detail |
|---|---|
| Slot-free output | Nothing written to `lines` or `gloss` contains `{`, `}` or `${` (D2 INV-3). |
| Labels never MT'd | `BuiltOption.label` is copied from the source verbatim. Labels appear in neither `lines` nor `gloss`. |
| Hints never MT'd | `BuiltBeat.hint` is copied verbatim (L1 only). |
| One record per (variant spec) | No record is shared between two different options, even when the rendered text coincides. |
| Idempotence | A second `bake` with unchanged inputs produces **zero diff**. This is checked in CI. |

### 5.3 Variant-key injectivity — the defect this doc found, and the amendment that fixed it

D2 §5.3's original composition was `beatId + '|' + slotNames.sort().map(n => n + '=' + value).join('|')`. **That is not injective when an option's read scope is empty.** Two options in one beat that read nothing both produced `"b6|"`, and because `lines` is `Record<variantKey, VariantRecord>` (D2 §7.1), one record **silently overwrote the other**. Silent data loss in a build artifact is the worst failure mode available here.

Minimal counterexample, from this doc's own content before I adjusted it: `b6` with an option template like `"No rush at all, later suits me better."` reads no slots, so both its options keyed to `"b6|"`.

**Amendment — approved and applied** (D2 §5.3, rule 1):

```
variantKey = [beatId, parentId, ...slotNames.sort().map(n => `${n}=${assignment[n]}`)].join('|')

parentId = Line.id        for a fixed-beat alternative
parentId = Option.key     for an option
```

Examples: `"b1|b1-l1"`, `"b3|b3-l1|spot=dinner-plan"`, `"b5|b5-l1|cuisine=chinese"`, `"b8|friends|who=friends"`.

This makes the key **injective by construction** — `Line.id` is unique in the conversation and `Option.key` is unique within its beat (D2 §4.3) — and it also removes the cosmetic trailing `|` produced when the read scope is empty. `VariantKeyOf` in `src/domain/types.ts` now takes the `parentId`.

**The amendment was admissible only because nothing had been baked yet.** No variant key or gloss key derived from one had been persisted, so the key space could change for free. That window is now closed: the formula is frozen for the life of the schema, and any future change is a rebake plus a full re-review.

**`E_VARIANT_KEY_COLLISION` remains a permanent guard, not a temporary one.** The amendment prevents two *different* alternatives from colliding; it does not prove the walk cannot emit the same key twice, and a build step that writes bytes must never trust that. Defence in depth costs one check.

## 6. `write` vs `check`

| | `check` | `write` |
|---|---|---|
| Validates phases 1–3 and 5–8 (and 4 when a translator is present, to compare rather than to write) | yes | yes |
| Writes the artifact | **never** | yes |
| Requires a translator | no | only to fill `mt` |
| Reports staleness | `E_SOURCE_STALE`, `E_TRANSLATOR_REV_STALE` | writes the fix, *then* reports what it changed |
| Exit code | non-zero on any `error` diagnostic | non-zero only on a hard failure |

`check` writing nothing is asserted by comparing the working tree before and after (AC-CONTENT-02).

## 7. Staleness and human-edit preservation

### 7.1 The three stored fields and the one derived flag

Per D2 §7.2: `l1` is the source of truth; `sourceHash` is the hash of the rendered `l1`; `mt` is the last machine output for `l1`; `l2` is the shipped Spanish. `edited = l2 !== mt` is **derived and never stored** (R4), so no author ever has to remember a flag.

`mt` is **immutable once written**. This is what makes `edited` permanent: a byte that a human chose can never later be mistaken for machine output, even if a regenerated translation would happen to coincide with it.

### 7.2 The rules table

| Situation | `write` does | `check` reports |
|---|---|---|
| `l1` unchanged, `l2 === mt` | nothing | clean |
| `l1` unchanged, `l2 !== mt` (human edit) | **nothing.** The edit is preserved forever. | clean, `edited: true` in the report |
| `l1` changed, `l2 === mt` | re-drafts `mt` from the new `l1`, sets `l2 = mt`, updates `sourceHash`, sets `reviewedBy: 'agent'`, `translationRev` = pinned | `E_SOURCE_STALE` |
| `l1` changed, `l2 !== mt` (edited **and** stale) | keeps `l2` **and** keeps `mt`, updates `sourceHash`, **clears `reviewedBy` to `null` and `triageRef`** | `E_SOURCE_STALE` + `E_UNREVIEWED` |
| `mt === ''` (never drafted) and a translator is available | drafts it | `E_SOURCE_STALE` if `sourceHash` differs, else clean |
| revision in the record ≠ the pinned revision | re-drafts, updates `translationRev` | `E_TRANSLATOR_REV_STALE` |
| a record is unreachable | reported; removed only with `--prune` | `E_ORPHAN_VARIANT` (warn) |
| a gloss key has no entry | cannot synthesise it without a translator; reported | `E_GLOSS_MISSING` (error) |
| `meta.reviewPolicy === 'fixture'` | stamps new records `reviewedBy: 'agent'`, `l2 = mt`, `translationRev = 'fixture-1'`; **never** `'owner'` | `E_UNREVIEWED`/`E_EDITED_NOT_OWNER` are warnings; `reviewedBy: 'owner'` is an error with its distinct message (D2 §7.2) |
| **the fixture is never drafted by `--author-only` write** | the committed fixture comes from `bake:fixture` (§2.4); `write` + no translator is not run against it | `--check --author-only` validates the committed artifact and exits 0 (E2) |

Three judgement calls inside that table, each deliberate:

1. **Write mode clears the review stamp when the English changed** (row 4). The Spanish a human approved was a translation of *different English*. Leaving the stamp would assert a review that did not happen. Clearing it makes the review debt show up in the diff, which is the point. The text is never touched.
2. **An edited record's `mt` is never overwritten** (rows 2 and 4). If a regenerated translation were allowed to replace `mt`, then `l2 !== mt` could become `l2 === mt` by coincidence and a human's choice would silently reclassify as machine output. Immutability prevents that.
3. **`mt === ''` is the sentinel for "no machine translation exists"** and pairs with `translationRev === null`. D2 §7.2 fixes `mt: string` and `translationRev: string | null`, so `''` is the consistent encoding rather than a type change. The invariant `(mt === '') === (translationRev === null)` is asserted everywhere (AC-ENG-19) and is what makes `E_TRANSLATOR_REV_STALE` well-defined in author-only mode:

   | record `translationRev` | meta `translator.en2romance` | Result |
   |---|---|---|
   | `null` | `null` | **clean** — an author-only artifact, no error (this is the PM's explicit requirement) |
   | set | set, equal | clean |
   | set | set, different | `E_TRANSLATOR_REV_STALE` |
   | **exactly one `null`** | | `E_TRANSLATOR_REV_STALE` with a distinct message ("artifact mixes translation provenance; rerun `bake`") |

   The asymmetric case is a corrupt or half-written artifact, not a valid state, and it must not be reported as a model problem.

### 7.3 Revision pinning (R3)

Revisions are **pinned revision ids** — a model commit or an `authored-<n>` table revision (amendment Y1) — never branches, and are recorded in `Conversation.meta.translator`. A moving model makes every build look stale, and — worse — lets the Spanish change without anyone editing anything. `E_TRANSLATOR_REV_STALE` is its own code precisely so model churn is never confused with authoring churn.

## 8. The review pipeline: draft → triage → adjudicate

### 8.1 Why it is a pipeline and not a checkbox

A translator drafts — a pinned model **or** an authored bilingual table; the one that ran is recorded in the artifact (D2 §7.2, amendment Y8). A separate review agent triages suspected errors; the owner adjudicates. The distinction that must survive forever is **which text a human actually read**, so it is a first-class field (`reviewedBy`) and not a comment (PM ruling Q1).

| Stage | Who | Output | Stamp |
|---|---|---|---|
| Draft | **the translator** (model or authored table) | `mt` for every line and every gloss span | — |
| Triage | **review agent** | a flag list of *suspected errors only*, target ~20% of targets | unflagged entries → `reviewedBy: 'agent'` |
| Adjudicate | **owner** | each open flag becomes `accepted` / `rejected` / `deferred` | `accepted`/`rejected` → `reviewedBy: 'owner'` + `triageRef`; `deferred` → `reviewedBy: null` (debt stays visible) |
| Gate | CI | `E_UNREVIEWED` on any `null` | — |

**The reviewer must not be the system that produced `mt`.** With **model** drafting that separation is automatic: the triage agent is not the model that produced `mt`. With an **authored table** it is **not** automatic — the same agent could author the table and then triage it, and a triage that is the drafter is theatre. That is exactly why the reviewer must run in a **fresh context** that reads only the output, whatever the drafting source; the approximation and its limits are stated in the next paragraph. The flag list records the reviewer's identity so this is auditable (§8.3).

**What `reviewedBy: 'agent'` may claim, and what it may not** (amendment Y7). `'agent'` asserts exactly one thing: *a triage pass ran over this entry in a fresh context and did not flag it.* It does **not** assert that the reviewer was independent in the strong sense. The approximation actually available is a **fresh context that reads only the output and carries no memory of writing it** — the *same underlying model* as the drafter when drafting is an LLM. That is a real check (a fresh context cannot defend a choice it does not remember making), but it is not a second, independent model, and the docs must not pretend otherwise. When drafting is a **model**, the separation is automatic and total, because the triage agent is not the model that produced `mt` at all; when drafting is an **authored table**, the table's author could be the triager, so the fresh context is what supplies the separation.

**No shipping flag list is shipped unless a triage actually ran.** A fabricated or silently-empty flag list that yields `'agent'` stamps would assert a review that did not happen — the same false provenance the field exists to prevent, and worse than shipping no flag list, which at least leaves the debt visible as `null` and `E_UNREVIEWED` red. `FLAG-REVIEWER-IS-DRAFTER` (§8.3) rejects a reviewer whose `model` equals the drafter's, and the fresh-context fact is recorded in `reviewer.contextId`. The M1 fixture's flag list is the honest exception: it names `model: 'no-triage-fixture'` with zero flags, so it records that no triage ran rather than pretending one did; its `'agent'` stamps are the recorded wart (D1 §10), bounded by `reviewPolicy: 'fixture'`.

Triage targets **suspected errors only**, not a rubric walk. An agent that flags 200 of 200 entries has produced a second draft, not a triage. The ~20% target and the flag rate are reported **against the flag list**, not by the coverage report (which takes no flag list — §9, amendment Y4), so over- and under-flagging are both visible.

### 8.2 What the agent is given, and what it must not be given

Given: the `l1`, the `l2`, the variant key, the substitution context (which surface form was inserted), the gloss span and its `l1`, the attention list in §11.6, and the `category` enum.

Not given, and not allowed to use: the browser, the UI, learner data, or the ability to draft. The agent flags; it does not rewrite. A `suggestion` is a suggestion.

### 8.3 Flag-list format (normative)

`review/flags.<conversationId>.json`. Structured and adjudicable, because review is delegated and the audit trail is the whole point.

```jsonc
{
  "conversationId": "m1-fixture",
  "sourceDigest": "sha256:v1:…",        // must equal meta.sourceDigest, else FLAG-STALE
  "translatorRev": "…",                 // the drafting revision these flags describe
  "reviewer": {
    "kind": "agent",                    // 'agent' | 'owner'
    "model": "…",                       // must differ from the drafting system
    "contextId": "…",                   // fresh-context evidence
    "ranAt": "…"                        // flags are a working artifact; a timestamp is allowed here
  },
  "targets": { "lines": 28, "glosses": 214 },
  "flags": [
    {
      "id": "F001",
      "target": "line",                                  // 'line' | 'gloss'
      "ref": "b8|friends|who=friends",                   // variant key, or normalizeSpan(span text)
      "en": "Perfect. I'll invite the whole crew.",
      "l2": "…",
      "severity": "high",                                // 'high' | 'medium' | 'low'
      "category": "idiom",
      "reason": "…",                                     // why it is suspect, one sentence
      "suggestion": "…",                                 // optional proposed correction
      "status": "open"                                   // 'open' | 'accepted' | 'rejected' | 'deferred'
    }
  ]
}
```

`category` enum (closed, and it maps to §11.6's attention list so flags are triageable):

`agreement` · `article` · `register` · `idiom` · `subjunctive` · `punctuation` · `false-friend` · `omission` · `addition` · `name` · `scope` · `other`

`scope` is for glosses whose rendering describes the whole clause rather than the hovered span — the failure mode `README §Translation` names.

### 8.4 Adjudication

The owner edits `status` on each flag — and, for an `accepted` flag, optionally supplies the final text in a `correction` field. Then:

```bash
bake --adjudicate review/flags.m1-fixture.json
```

- `accepted` **with** `correction` → `l2` is replaced, `reviewedBy: 'owner'`, `triageRef: <id>`. Because `mt` is immutable, the record becomes `edited` forever — correct, a human chose those bytes.
- `accepted` **without** `correction` → the owner read it and left it; `reviewedBy: 'owner'`, `triageRef: <id>`.
- `rejected` → the owner read it and disagrees; `reviewedBy: 'owner'`, `triageRef: <id>`.
- `deferred` → `reviewedBy` stays `null`, `triageRef: <id>`. **CI keeps failing.** There is no way to ship an unreviewed line, and "defer" is not a way to sneak one past the gate. If the owner wants to accept-as-is, that is `accepted` without a correction.

Provenance invariants (asserted):

1. Every `null`-stamped entry is an error (D2 `E_UNREVIEWED`).
2. Every `triageRef` resolves to a flag id whose `status` is `accepted` or `rejected`.
3. Every flag with those statuses has a corresponding `triageRef` on its target.
4. `edited === true` ⇒ `reviewedBy === 'owner'` (D2 `E_EDITED_NOT_OWNER`).
5. A flag list whose `sourceDigest` no longer matches is `FLAG-STALE` and must be regenerated — flags describe a specific revision of the English.

D6-local codes (these are **not** D2 `E_*` diagnostics; the flag list is D6's artifact):

| Code | Severity | Meaning |
|---|---|---|
| `FLAG-STALE` | error | `sourceDigest` ≠ `meta.sourceDigest`: regenerate the triage |
| `FLAG-REF-UNKNOWN` | error | a `ref` matches no variant key and no gloss key |
| `FLAG-DUP-REF` | error | two flags for the same `ref` |
| `FLAG-UNKNOWN-CATEGORY` | error | `category` outside the closed enum |
| `FLAG-REVIEWER-IS-DRAFTER` | error | the reviewer's `model` equals the drafting system's |
| `FLAG-OPEN` | warn | an `open` flag remains; the run reports but does not fail |

**`FLAG-REVIEWER-IS-DRAFTER` is the auditable half of §8.1's fresh-context rule** (amendment Y7). It can only compare the recorded `model` strings; it cannot detect a reviewer that is the same underlying model behind a different name, because a fresh context *is* that model. The check therefore enforces the naming discipline and the audit trail, and the fresh-context approximation is stated honestly in §8.1 rather than claimed to be independence. A `'fixture'` flag list names `model: 'no-triage-fixture'`, which is deliberately not the drafter's id and records that no triage ran.

## 9. Coverage report and the visibility-weighted ranking

`bake --report` writes `review/report.m1-fixture.md`. It is the owner's working surface and the project's most honest status page.

| Section | Contents |
|---|---|
| Counts | beats, choice beats, `lines` records, distinct gloss keys |
| Per beat | kind and the number of distinct variant keys, so an expensive beat is visible |
| Glosses | distinct span keys total, by level; entries by `origin` |
| Review status | `agent` / `owner` / `null` counts **separately for lines and glosses** |
| Review debt | every `null` entry with its `triageRef`, unfiltered — the queue |
| **Gloss priority** | the top 20 span keys ranked by **how many variants contain that span** |

**Four figures this section used to specify are deliberately not emitted** (amendment Y4), because `renderReport(conversation)` is a pure function of the **artifact**:

| Not emitted | Why |
|---|---|
| flags by category and severity | the report takes **no flag list**; the flag list (§8.3) is their source |
| flag rate vs the ~20% target | same; `REVIEW_FLAG_TARGET` is reported against the flag list, not the coverage report |
| `decisions` / sessions (`2^decisions`) | derivable from the choice beats but not currently printed; a session count is a property of the learner's run, not the artifact |
| a coverage percentage | coverage is guaranteed by construction — `E_GLOSS_MISSING` is a build error (D2 §9.4) — so the figure would always read 100% and teaches nothing |

Specifying rows that can never appear is exactly the drift this doc forbids elsewhere, so the table above lists what the report emits and this note records the four omissions.

**The gloss priority ranking is the feature that makes delegated review tractable.** ~200 spans is too many to triage evenly and too few to skip; ranking by variant coverage puts the owner's attention on the spans a learner is most likely to hover, because a span appearing in 8 of 28 lines is encountered 8 times more often than a span appearing once. The report gives that ordering for free, from data the pipeline already has.

It also keeps the review budget visible: **28 dialogue records and ~200 distinct gloss keys** (R12). That is small enough that mandatory review is affordable, and printing it is what keeps it affordable rather than assumed. The exact gloss count is an estimate until the first full bake; the report prints the real number, and if it is materially above ~250 the spine of a gloss needs rethinking rather than more review.

### 11.5 Hint discipline

Hints are the scaffolding channel and the easiest thing to ruin (README §Open questions, "how much hint text is too much"). **Six rules, and the split between what a machine can check and what only a reader can is stated explicitly** (amendment D3) — an AC whose predicate cannot be evaluated is not an AC.

| # | Rule | Enforced by |
|---|---|---|
| 1 | **≤ `HINT_MAX_CHARS` (60)**, one clause, sentence case | build: `HINT-TOO-LONG` |
| 2 | **No slots**, and therefore no interpolation (D2 §4.3) | build: `E_HINT_SLOT` (D2's registry — a slot in a hint is structurally invalid) |
| 3 | **No quotation marks** — none of `"`, `“`, `”`, `«`, `»`. A quoted span is a hint that hands over the line. The ASCII apostrophe is *not* in the set, so "Bobby's" is fine. | build: `HINT-ECHOES-LINE` |
| 4 | **No run of ≥4 consecutive tokens shared with any line of the same beat.** Tokenised on whitespace and punctuation, case-folded, accents significant; a choice beat is checked against *every* one of its options' lines. This is the mechanical half of "never quotes or paraphrases the line". | build: `HINT-ECHOES-LINE` |
| 5 | **Never reveals a choice's answer**; **one hint per beat**, so it can never vary by branch. If a beat seems to need two hints, the beat should be split. | review: §11.7 |
| 6 | **Does it read like a translation?** — the judgement half of rule 4. A hint that is a *paraphrase* rather than an *orientation* makes the learner read instead of listen, and no token-overlap threshold can decide that. | review only, §11.7 — **explicitly not mechanised** |

**Rule 4's mechanical check tokenizes the raw authored template, not the rendered line — a stated limitation** (amendment Y3). `checkHints` reads `line.template` / `option.template` verbatim, so the literal `{slotName}` is a token and the hint is compared against the *unsubstituted* text. Consequence: a hint that echoes a **substituted surface form** can pass. Worked example — the hint `"Ron says a nice dinner sounds great"` shares no 4-token run with the raw template `"Perfect, {spot} sounds great."`, but it shares five consecutive tokens with the rendered line `"Perfect, a nice dinner sounds great."`.

The **intended** rule is the rendered comparison, because the rendered line is what the learner hears; the current check is the weaker approximation, and catching a substituted echo is left to the review step (rule 6, §11.7 item 10). Why this is stated rather than fixed here: the check runs over the source **before** enumeration (D6 §14 rule 4), while the rendered comparison needs the walk's assignments, and requiring it without implementing it would make AC-CONTENT-16 assert something the build does not do. The honest move is to describe the check that exists and record the gap. If the owner wants the stronger rule, it is additive — run the same `sharesRun` against every rendered variant of the beat, which the pipeline already enumerates.

D6-local codes (they are authoring-quality rules, not schema validity, which is why they are not in D2's registry — see §12):

| Code | Severity | Meaning |
|---|---|---|
| `HINT-TOO-LONG` | error | a hint exceeds `HINT_MAX_CHARS` |
| `HINT-ECHOES-LINE` | error | a hint contains a double-quote character, or shares a ≥4-token run with a line of its beat **computed against the raw authored template** (the stated limitation, §11.5 rule 4) |

### 11.6 MT attention list

Predicting where `opus-mt-en-ROMANCE` will fail is what makes the triage tractable, and each line maps to a `category` in §8.3. The review agent gets this list; the owner's adjudication queue is ordered by §9's ranking.

| # | Phenomenon | Where | Category | Expect |

| 8 | Register drift into formal or written Spanish (`usted`, `¿Desea…?`) | all | `register` | medium |
| 9 | Length: MT sometimes drops or doubles a coordinated clause in longer sentences | b9 | `omission`, `addition` | medium |
| 10 | Standardisation of "Ron" / "Bobby" | b3, b10 | `name` | low |
| 11 | **False friends** — `actual`/`actualmente`, `realizar`, `embarazada`, `éxito`, `largo`. English words that map onto a Spanish word with a different sense | any | `false-friend` | low, but **high harm** — a false friend is confidently wrong and a learner will not catch it |
| 12 | **Gloss scope** — a gloss whose rendering describes the whole clause rather than the hovered span. The failure mode `README §Translation` names, and the reason §9.2 emits nested levels | glosses only, especially `line`-level spans | `scope` | **high for glosses** |
| 13 | **Other** — anything the twelve categories do not cover. Requires a `reason`, and a flag in this category is itself a signal that the enum needs a thirteenth value | any | `other` | low |

All twelve `category` values now appear here, which is what AC-CONTENT-19 asserts (amendment D2). `scope` was the specific omission worth fixing: it is the gloss failure mode the whole hover design exists to avoid, and it had no row.

### 11.7 Owner review checklist

Per flagged line, in order. The last item is the real gate.

1. **Proposition** — does the Spanish say what the English says, no more and no less? (`omission` / `addition`)
2. **Agreement** — gender and number hold across the *whole* sentence, especially where a substituted surface form sits.
3. **Register** — does it sound like two friends making plans? No `usted`, no idioms rendered literally.
4. **Punctuation** — `¿…?` and `¡…!` present and correctly paired.
5. **Substitution** — read the substituted variable in place; does it read naturally there?
6. **Names** — unchanged.
7. **False friends** — does any word look like an English word but mean something else?
8. **Gloss scope** — for a gloss, is it a rendering of *that span*, not of the clause?
9. **Pedagogy** — for a gloss, does hovering this teach the learner the right thing?
10. **Hints (§11.5 rules 5–6, review-only).** Two things a machine cannot decide: does this hint describe the *situation* rather than the answer, and does it read like a **paraphrase of the line** rather than an orientation to it? A hint that reads like a translation defeats the listen-first premise, and no token-overlap threshold can tell the difference between "Ron likes the idea" and "Ron says a nice dinner sounds great".
11. **The gate** — would you be comfortable showing this to a learner who cannot detect the error? If no, reject it and supply a correction.

**Registry additions — approved and applied.** `E_VARIANT_KEY_COLLISION` is in D2 §14 and in `DiagnosticCode`. `E_SENTINEL_IGNORED` is **not**, and the earlier text here claimed it was (amendment B2 / F2):

| Code | Home | Why |
|---|---|---|
| `E_VARIANT_KEY_COLLISION` | **D2 §14** and the frozen `DiagnosticCode` union | a source/walk validity rule |
| `E_SENTINEL_IGNORED` | **D6-local**, in `BakeDiagnosticCode` below | a property of the model, raised only by the bake program |
| `FLAG-*`, `HINT-*` | **D6-local**, in `BakeDiagnosticCode` | flag-list and hint-discipline validation |

D2 §14 is right to exclude it: the union must stay exactly the set the source and generated-artifact validators can raise. So this doc declares its own type, which is what makes AC-CONTENT-18 typeable without polluting the frozen union:

```ts
// tools/bake/diagnostics.ts — D6-local, never imported by src/**
type BakeDiagnosticCode =
  | 'E_SENTINEL_IGNORED'
  | 'FLAG-STALE' | 'FLAG-REF-UNKNOWN' | 'FLAG-DUP-REF'
  | 'FLAG-UNKNOWN-CATEGORY' | 'FLAG-REVIEWER-IS-DRAFTER' | 'FLAG-OPEN'
  | 'HINT-TOO-LONG' | 'HINT-ECHOES-LINE'
  | 'GLOSS-IDENTITY';          // §2.4: a self-gloss in a 'shipping' artifact
```

A `BakeDiagnostic` is `{ code: BakeDiagnosticCode; severity: Severity; path: string; message: string }` — the same shape as D2's `Diagnostic`, with a disjoint code set, so the two can be concatenated for reporting without either validator accepting the other's codes.

**`GLOSS-IDENTITY` is the fixture concession's guard** (§2.4): it fires when a `'shipping'` artifact has a gloss whose `l1 === mt === spanText`, i.e. a gloss that renders a span as itself. In a `'fixture'` artifact the same condition is **silent**, because that is how the fixture satisfies coverage. It is an error in shipping and nothing at all in a fixture — the policy is the whole distinction, which is why it needs no third severity.

**The check is scoped to `origin: 'mt'` entries** (amendment Y6), and that scope is not an escape hatch. The only authored-gloss route is the global `glossary.es.json` (D2 §3, §9.4); a conversation cannot privately relabel an identity gloss `origin: 'authored'` to dodge the guard. In practice every shipping gloss is `origin: 'mt'` and must be genuinely non-identity (§2.4).

**D2 path-list amendment — approved and applied.** The INV-1 boundary now lives in `tools/scan-excludes.json` as its single machine-readable copy (D5 §6), and names no bake path: the bake program lives in `tools/**` (§2.1), entirely outside the scan root. D2 §13 points at the JSON; `src/domain/types.ts` deliberately exports nothing for it.
